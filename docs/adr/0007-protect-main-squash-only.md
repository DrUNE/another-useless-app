# 0007. Защита `main` и слияние только через squash

Статус: принято (2026-10-31)

## Контекст

Работа ведётся через issue и pull request ([ADR-0001](0001-record-architecture-decisions.md),
раздел «Рабочий процесс» в `AGENTS.md`). Без технического ограничения это договорённость,
которую можно нарушить случайно: прямой пуш в `main`, слияние с красным CI, второй стиль
истории. Над репозиторием работают человек и ИИ-агент, и один из них может ошибиться.

## Решение

Правила закреплены в настройках GitHub, а не только в документах.

**Слияние** (Settings → General): разрешён только *squash*. Заголовок коммита берётся из
заголовка PR, тело — из сообщений коммитов. Merge-коммиты и rebase отключены. Влитые ветки
удаляются автоматически.

**Защита `main`** (Settings → Branches):

| Правило | Значение | Зачем |
|---|---|---|
| Обязательный PR | да, 0 одобрений | нет прямых пушей; одобрять некому, автор один |
| Обязательные проверки | `rust (cargo test)`, `ts (typecheck)` | нельзя слить красный PR |
| Актуальность ветки (`strict`) | нет | не заставляет перебазировать PR после каждого чужого слияния |
| Для администраторов | действует (`enforce_admins`) | владелец тоже работает через PR |
| Линейная история | да | следует из squash-only, проверяется явно |
| Force-push и удаление `main` | запрещены | история не переписывается |
| Разрешение обсуждений | обязательно | комментарии в PR не теряются |

Имена проверок должны совпадать с именами job в `.github/workflows/ci.yml`. Переименование job
без обновления защиты заблокирует все слияния.

## Альтернативы

- **Только договорённость в `AGENTS.md`.** Бесплатно, но держится на дисциплине. Агент или усталый
  человек её нарушит.
- **`strict` включён.** Надёжнее: в `main` попадает только то, что проверено на актуальной базе.
  Но при нескольких открытых PR каждое слияние требует обновить остальные и дождаться CI заново.
  Для одного автора с небольшими PR цена выше пользы.
- **Обязательное одобрение (1+).** Это основной смысл защиты в команде. Автор здесь один, и
  одобрить свой PR GitHub не даёт. Требование заблокировало бы работу. Если появится второй
  участник, это правило стоит включить.
- **Rulesets вместо классической защиты.** Новее и гибче (слои, обход по ролям), но для одной
  ветки и одного репозитория разницы нет. Перейдём, если правил станет много.
- **Администратор в обход (`enforce_admins` выключен).** Позволяет срочный пуш в `main`. Оставляет
  лазейку, которой пользуются именно тогда, когда проверки нужнее всего.

## Последствия

- (+) `main` всегда зелёный и с линейной историей: один коммит на PR с понятным заголовком.
- (+) Нарушить процесс случайно нельзя, ни людям, ни агентам.
- (+) Проверки (CI) становятся частью контракта, а не необязательной.
- (−) Даже мелкая правка требует PR. Исправление опечатки в README идёт тем же путём.
- (−) Нестабильный CI блокирует работу целиком (например, упавший сторонний action). Выход:
  временно ослабить правило в настройках и вернуть его, записав причину в issue.
- (−) Из-за `strict: false` возможна редкая ситуация, когда два PR по отдельности зелёные,
  а вместе ломают `main`. CI на `main` после слияния это поймает, но уже постфактум.
- (−) Настройки живут в GitHub, а не в репозитории: при переносе репозитория их нужно воссоздать.
  Эта запись служит их описанием.
