# 0006. Независимые сборки для каждой цели

Статус: принято (2026-10-31)

## Контекст

У проекта четыре цели: CLI, web, desktop и mobile. У каждой свой набор инструментов:

| Цель | Инструменты |
|---|---|
| CLI | Rust (`cargo`) |
| Web | bun, Vite, `wasm32` + `wasm-bindgen` |
| Desktop / Mobile | Tauri CLI, Rust, плюс Android SDK/NDK или Xcode (macOS) |

Если сборки зависят друг от друга, то для сборки одной цели потребуются инструменты всех:
установка Android SDK ради CLI, Rust-приложение Tauri ради web.

## Решение

Каждая цель собирается своей командой и без инструментов чужих целей:

- CLI: `cargo build -p app-cli --release`. Не требует Node, bun и Vite.
- Web: собирается из TS и WASM-пакета ядра. Не требует Tauri и мобильных SDK.
- Desktop и mobile: Tauri 2 в одном проекте (`apps/native`), различия в `capabilities` и `#[cfg(desktop)]` / `#[cfg(mobile)]`.

Общие части (`app-core`, `platform`, `ui`) — библиотеки, которые приложения подключают. Приложения
друг на друга не ссылаются. Направление зависимостей одностороннее: приложение → общее, никогда
наоборот. У каждой цели свой скрипт в корневом `package.json`.

## Альтернативы

- **Единая сборка «всё сразу».** Проще скрипт, но любой CI-запуск требует всех тулчейнов, а ошибка
  в одной цели блокирует остальные.
- **Отдельные репозитории по целям.** Полная изоляция, но общее ядро пришлось бы публиковать и
  версионировать как пакет, что для учебного проекта лишнее.

## Последствия

- (+) CI может запускать сборки параллельно и по затронутым путям.
- (+) Разработчик ставит только те инструменты, что нужны ему сейчас.
- (+) Границы между целями проверяемы: если CLI вдруг потребовал Node, это нарушение.
- (−) Нужно следить за границами: в монорепозитории легко случайно добавить импорт «не туда».
  Автоматическая проверка зависимостей запланирована отдельным шагом (дорожная карта, шаг 6).
- (−) Общий код обязан быть переносимым между всеми целями (см. [ADR-0002](0002-rust-core-wasm-for-web.md)
  и [ADR-0003](0003-ports-and-adapters.md)).
