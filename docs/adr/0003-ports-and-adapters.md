# 0003. Порты и адаптеры для ввода-вывода

Статус: принято (2026-10-31)

## Контекст

Файлы и сеть — основные возможности приложения. Но реализуются они по-разному:

| Платформа | Файлы | Сеть |
|---|---|---|
| CLI, Tauri (нативно) | `tokio::fs` | `reqwest` |
| Web (WASM) | OPFS через JS | `fetch` через JS |

Если ядро вызывает `tokio::fs` напрямую, оно не соберётся под WASM, и его нельзя проверить
без реального диска и сети.

## Решение

Ядро описывает *что* ему нужно, а не *как* это делается. В крейте `app-core` есть порты
(trait `Fs` и `Http` в `crates/core/src/ports.rs`). Use-cases принимают их обобщённо:

```rust
pub async fn save_url<H: Http, F: Fs>(http: &H, fs: &F, url: &str, path: &str) -> Result<SaveReport, FetchError>
```

Реализации (адаптеры) живут вне ядра:

- `crates/platform-native`: `NativeFs`, `NativeHttp` для CLI и Tauri.
- web: адаптеры на JS (OPFS и `fetch`), будут в шаге 3.
- тесты: фейки в памяти (`MemFs`, `FakeHttp`).

Адаптеры подключает **только точка входа** приложения. Для TS-стороны то же устроено
в `packages/platform` (`Platform`, `hasCapability`, `requirePort`): отличия платформ выражаются
наличием порта, а не проверками `if (isTauri)`.

Для читающих с опытом TS: trait в Rust похож на `interface`, но принимается обычно через
дженерики (`F: Fs`), и компилятор генерирует отдельную версию функции под каждый тип
(мономорфизация), без вызова через таблицу. Динамическая диспетчеризация (`dyn Trait`)
возможна, но здесь не нужна.

## Альтернативы

- **Прямые вызовы `tokio::fs` и `reqwest` в ядре.** Проще, но ядро теряет переносимость
  и тестируемость.
- **Условная компиляция `#[cfg(target_arch = "wasm32")]` внутри ядра.** Смешивает логику
  и платформенный код, растёт число веток, трудно тестировать каждую.
- **`dyn Trait` вместо дженериков.** Гибче в рантайме, но требует `Box<dyn Future>` или макросов
  для async-методов; выигрыша для нашего случая нет.

## Последствия

- (+) Ядро собирается под любую цель и тестируется на фейках без сети и диска.
- (+) Новая платформа = новый адаптер, без изменений ядра.
- (+) Прикладной код не знает о платформе.
- (−) Больше кода и косвенности: интерфейс нужно проектировать заранее.
- (−) Порт должен описывать общий минимум. Платформа с уникальной возможностью (например, мобильная)
  получает её через новый порт, а не через «просочившийся» вызов.
- (−) Дженерики распространяются по сигнатурам (`<H: Http, F: Fs>`). Если число портов вырастет,
  их стоит собрать в одну структуру-контекст.
