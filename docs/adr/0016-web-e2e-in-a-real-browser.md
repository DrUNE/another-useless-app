# 0016. Сквозные тесты веба в настоящем браузере

Статус: принято (2026-10-31). Дополняет [ADR-0013](0013-wasm-boundary-tests-in-typescript.md) и [ADR-0014](0014-ui-core-boundary.md).

## Контекст

Тесты на bun и vitest не видят то, что происходит только в браузере: OPFS, `fetch` с ограничениями CORS, загрузку и запуск WASM, то, как ошибка ядра превращается в текст на экране. ADR-0013 и ADR-0014
оставляли этот сценарий ручной проверкой («в CI пока не входит»). Ручная проверка устаревает со следующим изменением.

## Решение

Пакет `tests/e2e` (`@app/e2e`) с тестами на `vitest` и `playwright-core`:

- тест поднимает собранный `apps/web/dist` и два «чужих» источника (с заголовками CORS и без) на случайных портах и проверяет 8 сценариев: запуск на WASM-ядре, запись в OPFS, сохранность
  файла после перезагрузки, ошибки `status`, `invalidPath` (политика из общего ядра) и `network` (нет CORS), успех при разрешённом CORS и тишину в консоли на успешном пути;
- каждый тест получает чистый профиль браузера, значит, пустой OPFS и независимость сценариев;
- **браузер не скачивается:** используется установленный Chrome или Chromium, путь задаёт `CHROME_PATH` либо берётся из типичных мест (Linux, macOS, Windows);
- **без браузера тест пропускается с предупреждением, а при `E2E_REQUIRE_BROWSER=1` падает.** CI всегда включает эту переменную: иначе отсутствие браузера делало бы набор «зелёным» и бессмысленным;
- запуск: `bun run test:e2e` (собирает web и гоняет тесты); в CI шаг стоит в job `wasm`, где web уже собран. Обычный `bun run test` этот пакет не запускает (у него нет скрипта `test`).

## Альтернативы

- **`@playwright/test` со скачиваемыми браузерами.** Удобный раннер, но тянет собственный ~150 МБ браузер в CI и контейнер и вводит второй раннер рядом с `vitest`. Нам нужен один раннер и уже установленный Chrome.
- **Cypress, WebDriver.** Тяжелее и избыточны для восьми сценариев.
- **Оставить ручную проверку.** Дёшево сегодня, но сценарий молча устаревает.
- **Запускать в браузере сами Rust-тесты WASM (режим браузера у `wasm-bindgen-test`).** Проверяет ядро, а не интерфейс целиком: не видит UI и OPFS-адаптер.

## Последствия

- (+) Проверяется целая цепочка в реальной среде: UI, WASM-ядро, мост портов, адаптеры OPFS и `fetch`, перевод ошибок в текст. Проверено намеренными поломками: сломанный текст ошибки в UI и убранная в ядре проверка `..` роняют по одному
  нужному тесту.
- (+) Работает на bun без Node.js (проверено в контейнере с установленным Chromium) и на Node; в CI используется Chrome раннера.
- (−) Нужен Chrome или Chromium. В devcontainer браузера нет, чтобы не раздувать образ (он уже 4,5 ГБ), поэтому в контейнере тест пропускается; запускайте на хосте или установите `chromium` в контейнер.
- (−) Версия Chrome на раннере не закреплена: обновление раннера может сломать тест (и это будет честным сигналом, а не ложным зелёным).
- (−) Проверяется только Chromium: Safari и Firefox не охвачены (поддержка `createWritable` в OPFS у браузеров различается).
- (−) Тесты ходят на `127.0.0.1`: это «потенциально доверенный» источник, где OPFS доступен; поведение на небезопасном источнике (обычный HTTP по имени хоста) не проверяется.
