# 0020. Двуязычная документация и английские API-справки

Статус: заменено ADR-0021 (2026-11-02)

[English version](0020-bilingual-docs-and-api-reference.md)

## Контекст

Документация проекта должна быть доступна на русском и английском. Обычные комментарии в коде
остаются на русском, а API-справки и краткая документация функций при релизе должны быть на
английском. Release workflow для документации отсутствует, генератор TypeScript-документации не
установлен. Два языка не должны приводить к коммиту generated files или переписыванию принятых ADR.

## Решение

1. **Английский — язык по умолчанию.** Новые Markdown-документы сохраняют обычное имя
   (`README.md`, `docs/adr/0020-*.md`), русский перевод лежит рядом с суффиксом `.ru.md`. Файлы с
   закреплёнными GitHub именами могут содержать оба языка внутри одного файла. Каждый новый документ
   имеет обе версии и перекрёстные ссылки. Существующие русские файлы мигрируются отдельными PR;
   тест согласованности содержит явный список legacy-исключений. Решения принятых ADR не
   переписываются: перевод добавляется как отдельная языковая версия.
2. **Обычные и API-комментарии различаются.** Обычные `//` комментарии остаются на русском. Новые
   Rustdoc (`///`, `//!`) и TSDoc (`/** ... */`) пишутся на английском. Существующие API-комментарии
   переносятся отдельными PR. Сгенерированные файлы, включая `bindings.ts`, вручную не правятся.
3. **HTML генерируется локально и при релизе.** `bun run docs` собирает WASM-границу, запускает
   `cargo doc --workspace --no-deps` для всех Rust-крейтов и TypeDoc для TS-пакетов, приложений,
   утилит и E2E-тестов. TypeDoc использует `entryPointStrategy: "packages"`, версия закреплена через
   catalog. Результат попадает в игнорируемый `target/docs`.
4. **Публикация — GitHub Pages.** Release workflow загружает сайт в GitHub Pages. Сгенерированный
   HTML не коммитится. Ручной запуск workflow разрешён для проверки и восстановления.
5. **Пары проверяются автоматически, перевод — человеком.** Тест согласованности проверяет наличие
   обеих версий у каждого не legacy документа. Эквивалентность и актуальность перевода он не доказывает.

## Альтернативы

- **Только английский или только русский.** Проще, но отсекает часть аудитории и не решает задачу
  релизной документации.
- **Два языка в каждом файле.** Не нужно соглашение имён, но длинные тексты труднее читать и
  редактировать, а ссылки на конкретный язык невозможны. Исключение — файлы для GitHub.
- **Перевести всё одним PR.** Инфраструктура смешалась бы с сотнями переведённых строк, а ревью
  стало бы формальным. Постепенная миграция даёт действующие правила уже с первого PR.
- **Коммитить generated HTML.** Ссылки удобны, но diff большой и сразу устаревает. CI artifacts и
  GitHub Pages — результат публикации, а не исходники.
- **Машинный перевод в CI.** Неконтролируемое смысловое расхождение. Переводы пишутся и
  проверяются как исходные документы.

## Последствия

- (+) Новая документация двуязычна, а поиск и краткие API-справки имеют единый английский источник,
  пригодный для релизов.
- (+) Локальная и release-генерация используют одну команду и закреплённые инструменты репозитория.
- (+) Legacy не блокирует правила: новый файл без языковой пары падает тестом.
- (−) Каждое изменение требует двух переводов и ревью обоих.
- (−) Тест пар не обнаруживает устаревший или некачественный перевод.
- (−) GitHub Pages должен быть включён, workflow нужны соответствующие разрешения.
- (−) Существующие русские API-комментарии останутся в generated output до отдельных миграционных PR.
