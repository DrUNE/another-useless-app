# 0015. Проверка объявленных зависимостей: правила как данные

Статус: принято (2026-10-31)

## Контекст

Архитектурные границы проекта записаны в ADR: ядро без платформенных зависимостей ([ADR-0002](0002-rust-core-wasm-for-web.md)), порты ни от чего не зависят
([ADR-0003](0003-ports-and-adapters.md)), CLI не тянет Tauri, web не тянет Tauri, приложения не зависят друг от друга ([ADR-0006](0006-independent-builds.md)), UI знает
только контракт ядра ([ADR-0014](0014-ui-core-boundary.md)). Линтер ([ADR-0011](0011-oxc-lint-and-format.md)) проверяет **импорты**, а это не то же самое, что **объявленные
зависимости**: крейт может подключить Tauri в `Cargo.toml`, ничего не импортируя, или получить его транзитивно через другой крейт. Сборка под wasm32 ловит только часть таких случаев.

## Решение

Инструмент `tools/boundaries` (`bun run boundaries`) сверяет реальные графы зависимостей с правилами, которые лежат данными в `tools/boundaries/rules.json`.

- **Rust:** граф берётся из `cargo metadata --locked --filter-platform <платформа>`. Платформа указана в правиле: `host` (та, на которой идёт проверка) или цель вроде
  `wasm32-unknown-unknown` для `app-core-wasm`.
- **TS:** граф берётся из `package.json` пакетов воркспейса; зависимости пакетов воркспейса раскрываются, внешние пакеты считаются листьями.
- **Два вида правил:** `directOnly` (исчерпывающий список прямых зависимостей, например у `app-core` только `thiserror`) и `forbidTransitive` (запрещённые крейты или пакеты
  среди всех достижимых; нарушение показывает кратчайшую цепочку, например `app-core-wasm → app-core → tokio`). Разрешены и шаблоны (`@tauri-apps/*`).
- **Устаревшее правило не молчит:** если крейта или пакета из правила уже нет, проверка падает с ошибкой (код 2), а не проходит.
- **Где запускается:** Rust-часть требует Rust, скачанные крейты и bun, поэтому шаг стоит в job `wasm`. TS-часть дополнительно входит в `bun run test` (тест «репозиторий соблюдает правила»).

## Находка, определившая дизайн

Без `--filter-platform` граф `app-cli` и `app-platform-native` содержал `wasm-bindgen`, `js-sys` и `web-sys`. Они не зависимости CLI: это ветка `reqwest` для сборки под wasm32,
которую `cargo metadata` показывает вместе со всеми платформами. Правило «CLI не тянет браузерные крейты» на таком графе дало бы ложные срабатывания, поэтому граф строится
для конкретной платформы.

## Альтернативы

- **`cargo-deny`.** Стандартный инструмент для запретов, лицензий и уязвимостей, но смотрит на граф целиком, а правило «у этого крейта допустимы только такие зависимости» выражается
  через `wrappers` неудобно. Его польза другая (RUSTSEC и лицензии) и выходит за эту задачу; её можно добавить отдельно.
- **`dependency-cruiser` и аналоги для TS.** Проверяют импорты, а они уже проверяются линтером; нам нужны объявленные зависимости.
- **Разбор вывода `cargo tree` в скрипте CI.** Хрупко и не проверяемо тестами.
- **Одна лишь сборка под wasm32.** Не ловит CLI с Tauri или web с Tauri.

## Последствия

- (+) Нарушение правила ломает проверку и объясняет причину (`why` со ссылкой на ADR) и путь зависимости. Проверено намеренными нарушениями в настоящих манифестах: CLI с `wasm-bindgen`,
  ядро с `tokio`, WASM-привязка с `reqwest`, web с Tauri, UI с мостом WASM, нативное приложение с web (все шесть дают ошибку).
- (+) Логика покрыта 13 тестами на подменённых графах; правила хранятся данными, и их можно читать как перечень архитектурных ограничений.
- (−) Правила нужно обновлять вместе с архитектурой. Новая граница без нового правила никем не охраняется.
- (−) TS-граф раскрывается только по пакетам воркспейса: зависимости внешних пакетов (например, плагина Vite) не разворачиваются.
- (−) Проверка Rust идёт на платформе хоста: правила проверялись на Linux; на macOS и Windows (граф хоста там другой) до матрицы CI (#27) не проверялись.
- (−) Не проверяет импорты (это делает линтер), а потому две проверки нужно держать согласованными.
