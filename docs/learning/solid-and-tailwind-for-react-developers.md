# Solid 2 и Tailwind 4 для разработчика на React

Конспект к `apps/web`. Основа — официальный `CHEATSHEET.md`, который лежит в пакете
(`node_modules/solid-js/CHEATSHEET.md`), плюс то, что мы проверили в этом проекте.
Solid 2 сейчас в статусе RC: **туториалы и ответы по Solid 1.x вводят в заблуждение**, а
знания о React тоже мешают, если отнестись к ним как к картам местности.

## Главное: компонент выполняется один раз

В React функция компонента вызывается заново на каждый рендер, и весь JSX строится снова.
В Solid функция вызывается **один раз**. Дальше обновляются только те места JSX, где был вызван
сигнал. Посмотрите `apps/web/src/SaveForm.tsx`: `createSignal` в теле создаётся единожды, а
`{busy() ? "Сохраняем…" : "…"}` — это маленькая подписка на `busy`, а не перерисовка компонента.

Следствия, из-за которых «похожий на React» код ломается:

- нельзя читать сигнал «просто так» в теле компонента: прочитанное значение останется навсегда
  (в dev-режиме Solid предупреждает); читают в JSX, в `createMemo` или в обработчиках;
- нет «зависимостей» и «замыканий с устаревшим значением» в привычном смысле, но есть свои
  ловушки (см. таблицу).

## Похоже на React, но работает иначе

| React | Solid 2 | В чём разница |
|---|---|---|
| `const [n, setN] = useState(0)` | `const [n, setN] = createSignal(0)` | `n` — **функция**, читается как `n()`. Передача `n` вместо `n()` отдаст дочернему компоненту функцию, а не число. |
| `setN(1); n` (старое значение в замыкании) | `setN(1); n()` | Тоже старое, но по другой причине: запись применяется на ближайшем microtask или после `flush()`. |
| `useEffect(fn, [deps])` | `createEffect(compute, apply)` | Две функции: `compute` отслеживает чтение сигналов, `apply` делает побочный эффект без отслеживания. Массива зависимостей нет. Эффект не сравнивает значения: чтобы не срабатывать зря, читайте `createMemo`. |
| `useMemo` | `createMemo` | Зависимости отслеживаются сами. |
| `function C({ title })` | `function C(props)` и `props.title` | **Деструктуризация убивает реактивность**: значение читается один раз. Чтение `props.title` в JSX и есть подписка. |
| `<C value={n} />` | `<C value={n()} />` | Родитель отдаёт значение, а не геттер. |
| `cond ? <A/> : <B/>`, `list.map(...)` | `<Show when>`, `<For each>` | Работает и тернарник, но Show/For обновляют только изменившееся и сохраняют DOM. |
| `key={id}` | `<For each>` по умолчанию ключует по ссылке; `keyed={false}` — по позиции | Во `For` без `keyed={false}` `item` — **значение**, а индекс `i` — функция. С `keyed={false}` наоборот. |
| `className="a " + (b ? "b" : "")` | `class={["a", { b: b() }]}` | Атрибут называется `class`. Массив и объект собирают классы сами, строки склеивать не нужно. |
| `useContext`, `<Ctx.Provider value>` | `useContext`, `<Ctx value>` | Сам контекст и есть провайдер. Без провайдера — ошибка, а не `undefined`. |
| `useRef` | `ref={(el) => …}` | Ref — функция, объектов-ссылок нет. |
| `useEffect(..., [])` для монтирования | `onSettled(() => …)` | Работает и в теле компонента, и в обработчиках; возвращённая функция — очистка. |
| `<Suspense>`, `<ErrorBoundary>` | `<Loading>`, `<Errored>` | Асинхронность — это вычисление, возвращающее Promise; `createResource` из 1.x удалён. |
| Controlled input `value={s}` | `value={s()}` + `onInput` | Значение записывается в DOM-свойство при каждом перезапуске привязки, а не сравнивается с DOM. Пример: `src/Field.tsx`. |

## Что изменилось по сравнению с Solid 1.x

Это отдельный источник ошибок при поиске в интернете и в подсказках ИИ:

- DOM-часть живёт в `@solidjs/web`: `render` импортируется оттуда, `jsxImportSource` в tsconfig — `@solidjs/web`.
- Плагин Vite переименован в `@solidjs/vite-plugin` (старый `vite-plugin-solid` — только реэкспорт).
- `Suspense` → `Loading`, `ErrorBoundary` → `Errored`, `mergeProps` → `merge`, `splitProps` → `omit`,
  `onMount` → `onSettled`, `createEffect` обязан принимать две функции.
- Запись в сигнал из тела компонента или из вычисления — ошибка в dev; пишут из обработчиков.

## Tailwind 4: как это устроено у нас

- **Utility-first.** Стили — классы прямо в разметке (`rounded-control px-4 py-2`). Не нужно придумывать
  имена классов и искать, где они лежат. В сборку попадают только использованные классы: CSS
  всего приложения сейчас около 7,6 кБ.
- **Токены в одном месте.** `packages/config/theme.css` задаёт `@theme { --color-surface: …; --radius-control: … }`.
  Каждая такая переменная становится утилитой: `bg-surface`, `text-ink`, `rounded-control`. Тёмная тема
  переопределяет переменные в `@media (prefers-color-scheme: dark)`, компоненты не меняются.
- **Модификаторы.** `pointer-coarse:py-3` применяется на сенсорных экранах, `border-ink/20` задаёт прозрачность,
  `focus-visible:outline-2` — состояние. Так адаптивность и платформенные отличия остаются в классах.
- **`@source`.** Tailwind сам сканирует проект приложения; пакеты монорепозитория (`ui`, `app`, `features`)
  указаны в `theme.css`, чтобы классы из них тоже попадали в сборку.
- **Без `@apply`.** В v4 его не рекомендуют: вместо него выделяйте компонент (`Field.tsx`), а не CSS-класс.

## Как это проверено

`bun run typecheck` и `bun run build:web` проходят, а сценарий в headless Chromium (dev-сервер Vite)
подтвердил: пустое состояние, блокировка кнопки на время запроса, добавление записи в начало списка,
показ и сброс ошибки, применение токенов темы, переключение на тёмную схему. В консоли dev-режима нет
предупреждений Solid.

## Контекст: так ядро попадает в интерфейс

В проекте UI получает ядро через контекст (`packages/app/src/core-context.ts`), а точка входа его подставляет. Выглядит как React, но отличается:

| React | Solid 2 | В чём разница |
|---|---|---|
| `<Ctx.Provider value={x}>` | `<Ctx value={x}>` | Сам контекст и есть провайдер. |
| `createContext(defaultValue)` | `createContext<T>()` без значения | Без провайдера `useContext` **бросает ошибку**, а не возвращает `undefined`: UI не запустится с «никаким» ядром. |
| хук-обёртка `useX()` с проверкой на `undefined` | не нужна | Проверка уже внутри `useContext`, значение типизировано как `T`. |
| смена значения контекста перерисовывает потребителей | перерисовки нет | Тело компонента выполняется один раз. Нужна реакция на изменения: кладите в контекст сигналы. |
| состояние на уровне модуля | создавайте внутри провайдера | Значение на уровне модуля разделяют все запросы при серверном рендеринге; у нас ядро создаётся в точке входа внутри `render`. |

Ещё деталь из `apps/web/src/index.tsx`: ядро в WASM грузится асинхронно, поэтому точка входа сначала дожидается `createCore(...)` и только потом вызывает `render`
(при сбое показывает сообщение вместо пустой страницы). Это обычный `await` на верхнем уровне модуля, а не особенность Solid.

## Линтер подсказывает привычки из React

`bun run lint` (oxlint с плагином `eslint-plugin-solid`, ADR-0011) отдельно ловит то, что `tsc` пропускает:

| Привычка из React | Правило | Что скажет линтер |
|---|---|---|
| `function C({ title })` | `solid/no-destructure` | деструктуризация props ломает реактивность |
| `className`, `htmlFor` | `solid/no-react-specific-props` | в Solid атрибуты называются `class` и `for` |
| `dangerouslySetInnerHTML` | `solid/no-innerhtml` | используйте `innerHTML` (и помните про XSS) |
| `useEffect(fn, [deps])` | `solid/no-react-deps` | массива зависимостей нет, отслеживание автоматическое |
| `items.map(...)` в JSX | `solid/prefer-for` | `<For>` обновляет только изменившееся |
| чтение `count()` в теле компонента | `solid/reactivity` | значение прочитается один раз и не обновится |

Правила написаны под Solid 1.x, поэтому мы включили только те, что проверены на коде Solid 2. Чего линтер не видит, ловят
предупреждения самого Solid в dev-режиме и сквозные проверки.
